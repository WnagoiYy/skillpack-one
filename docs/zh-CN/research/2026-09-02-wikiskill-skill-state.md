# WikiSkill 与 SKILL.state：对 SkillPack One 的启发

日期：2026-09-02  
来源：arXiv 官方 PDF，[WikiSkill](https://arxiv.org/pdf/2608.27454) v1 与 [SKILL.state](https://arxiv.org/pdf/2608.26263) v2。  
决策问题：在不改变 Category → Atom → Capability Pack → Meta 的前提下，哪些机制值得采用？

## 直接结论

两篇论文作用于不同时间尺度，彼此互补：

| 论文 | 时间尺度 | 主要状态 | 在 SkillPack One 中的归属 |
| --- | --- | --- | --- |
| WikiSkill | 多轮优化之间 | 已积累的成功/失败模式与干预结果 | 元治理下的 Evolution Knowledge |
| SKILL.state | 一次长任务内部 | 对后续行动仍有用的当前世界/流程状态 | 能力包的可选 runtime-state profile |

两者都不需要增加新的 Skill 类型。分类仍负责需求路由，原子仍保持单一能力边界，能力包负责编排，元 Skill 负责生命周期治理。

## 论文实际证明了什么

### WikiSkill

WikiSkill 将不可变原始轨迹、沉淀模式与影响日志的持久 Wiki、可回滚的活动 Skill 分开。执行任务的 Inference Agent 只使用活动 Skill，明确不能访问 Wiki；Maintainer 和 Proposer 可以读取 Wiki 与选定轨迹。每轮只提出一个原子 Skill 修改，只有验证集提升才接受，但无论接受还是拒绝，Wiki 知识都会保留。

论文覆盖五个基准和五个模型。表 1 对三次独立进化运行取平均，并使用 1,000 次成对 bootstrap。WikiSkill 在每个模型的平均结果上都是论文报告的最高值。最关键的消融是表 3：Inference Agent 不访问 Wiki 时，让 Proposer 访问 Wiki，四基准平均从 48.7% 提升到 63.7%；反过来把 Wiki 暴露给 Inference Agent，会把默认配置从 63.7% 降到 60.9%。

跨模型迁移同时给出正面结果和警告。进化程序经常可以迁移，但表 2 也出现严重负迁移：Qwen-3.5-4B 生成的表格 Skill 使 Gemini-3.5-Flash 从无 Skill 的 50.5% 降到 18.1%。作者将其归因于小模型专用 workaround 和碎片化诊断流程限制了更强模型。

重要局限：论文直接注入完整 Skill，没有测试检索；验证集较小；Wiki 没有自动清理；严格的即时提升门禁可能拒绝铺垫型修改；测试没有覆盖数百动作或数小时任务。

### SKILL.state

SKILL.state 用“不可变过程规范＋当前结构化状态＋最新观察”替代不断追加的对话历史。模型可以在单步内推理，但跨步只保留通过验证的状态补丁和动作。在过程、状态与观察大小有界的假设下，单步上下文相对任务长度为 O(1)，累计提示词为 O(T)，而不是回放历史导致的 O(T²)。

论文在五个随机种子的两种 SkillExecBench 环境，以及 InterCode CTF 和 Sierra τ-Bench 上评测。仓库任务 100 步时，表 1 报告 SKILL.state 使用 65,408 tokens、准确率 0.94；带完整历史的 Stateful 基线使用 1,062,387 tokens、准确率 0.91。200 步时分别是 122,384/0.94 与 5,041,164/0.88。公共任务表 4 中，SKILL.state 在三个任务上的完成率都是论文报告的最高值，累计 token 也低于对照运行时。

同 token 预算对照很重要：单纯截断或压缩历史表现很差。因此论文支持的是“显式充分状态”，而不是随意删上下文。

重要局限：当状态结构需要动态发现、早期观察的未来价值当时未被识别，或者历史本身就是目标产物（审计、调试、来源解释）时，固定状态并不安全。多 Agent 并发写入需要冲突解决。较小模型还经常出现提前删除/覆盖、类型错误和 JSON 格式错误，所以确定性合并与 Schema 验证是必要条件，但不能证明语义正确。

## 已采纳

1. **Evolution Knowledge，而不是第五种 Skill。** `.skill-system/knowledge/` 保存不可执行、有范围、有证据、可取代并有生成索引的模式；原始运行、知识模式和活动 Skill 相互分离。
2. **知识只服务元治理。** 普通任务不读取模式层；提案引用相关模式 ID，晋级和拒绝结果都保留为证据。
3. **保留来源的可清理语义。** 不照搬 WikiSkill 永不清理的 Wiki；模式可被取代或归档，但不能静默删除。
4. **能力包按需声明当前状态。** 能力包可以声明 JSON Schema、初始状态、JSON Merge Patch 和独立审计日志策略；首个 profile 用于 `safe-skill-evolution`。
5. **提交前验证。** 当前状态和候选补丁都必须通过确定性验证；补丁失败不能改变现有状态；原型污染键直接拒绝。
6. **历史移出活动上下文，不是销毁。** 运行提示可以只使用当前状态，但不可变审计证据仍用于治理、来源、调试与回滚。

## 调整采纳或暂缓

- 自动轨迹抽样、Wiki Maintainer 自动生成和自治 Skill 提案循环暂缓，直到存在权限受控的真实轨迹与独立验证器。
- runtime-state profile 是可选且能力包专属的，不存在通用状态 Schema，也不强制删除历史。
- Pi 与 Codex 适配器尚未通过该状态循环执行真实长任务。本版本只认证 Schema、补丁和组合机制，不宣称复现论文的 token 或准确率收益。
- WikiSkill 指出严格门禁的局限，但铺垫型中性修改仍需分阶段证据，不能自动放行。
- 多 Agent 合并、约束解码、语义状态验证、状态遥测和长任务认证继续暂缓。

## 明确不采纳

- 用任一论文的本体替换现有四层架构。
- 让普通任务 Agent 直接访问 Evolution Knowledge。
- 自动晋级生成的 Skill，或只凭一个验证总分上线。
- 把模型专用 workaround 当作通用可迁移程序。
- 对解释、调试、合规或来源任务丢弃审计历史。

## 置信度与停止条件

两种机制分别落在既有层级的判断置信度高，因为它直接对应论文系统边界和仓库现有契约。它们能提升 SkillPack One 真实运行的置信度为中等：目前还没有 Pi 模型提供商的真实长任务 Skill Lift。研究在阅读全文、核对主要架构图、结果表、消融、提示词、附录和局限后停止；继续收集二手评论不太可能改变当前工程取舍。
