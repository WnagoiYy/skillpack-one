# 可自组织 Skills：架构设计

**状态：** 已接受的设计基线  
**日期：** 2026-09-02  
**主语言：** 英文；同时维护中文伴随文档

## 1. 愿景

构建一个开放、兼容 Codex 的系统，把大量互相重叠的 Agent Skill 与 MCP Server，整理成少量可组合、可测试的原子能力。这个集合需要能够解释自己的分类，分别评估“是否命中”与“是否完成”，依据证据进化，并在失败时安全回滚。

它不是把热门 Skill 全部装进来的大礼包，而是一套 Skill 操作系统：

1. **分类 Skill**：先把请求缩小到能力领域。
2. **原子 Skill**：在明确契约内完成一种边界清晰的能力。
3. **配方/能力包**：像插件一样组合原子 Skill 与 MCP 依赖，完成真实任务。
4. **元 Skill**：治理发现、分类、变更、评估、上线、弃用与回滚，包括治理自己。
5. **训练与评测器**：上线前分别测量路由、流程遵循、任务完成、回归、安全、成本和延迟。

## 2. 核心约束

- 通过 `.agents/skills/<skill-name>/SKILL.md` 保持 Codex 原生发现能力。
- 通过 `.codex-plugin/plugin.json` 将同一份源码打包为 Codex 插件。
- 逻辑上采用“先分类、再原子”的两阶段路由。
- 分类边界来自用户真正想得到的结果，而不是作者、仓库或工具品牌。
- 建立不少于 300 项的前沿 Skill/MCP 可追溯目录，但不盲目安装和执行第三方代码。
- 根据能力契约识别重复，并从现有项目中提炼原子能力候选。
- 英文作为生态兼容的主入口，中文采用 `index.zh-CN.md`；兼容 `*.zh.md` 回退。
- 首个真实测试底座采用 Pi；DSH 与 Codex 通过统一适配层接入。
- 自优化只能产生有边界、可审查的补丁，必须通过留出集和安全门禁。

## 3. 方案选择

### 方案 A：物理嵌套目录

把原子 Skill 放进分类目录。结构直观，但不同 Agent 对嵌套发现的支持不稳定，而且重新分类会改变 Skill 路径和身份，因此不采用。

### 方案 B：原生 Skill 平铺 + 分类索引 + 机器注册表（采用）

所有可调用 Skill 都是 `.agents/skills` 的直接子目录。分类 Skill 也是标准 Skill，通过中英文索引逐步披露原子能力；机器可读契约和注册表负责两阶段路由、去重、评测和组合。

这个方案同时满足 Codex 原生兼容、稳定身份、插件分发和确定性测试。

### 方案 C：数据库里的万能路由器

动态性很强，但会形成单点瓶颈，弱化 Codex 的原生 Skill 可见性与渐进披露，因此不作为主架构。

## 4. 核心结构

```text
.codex-plugin/plugin.json       Codex 插件清单
.agents/skills/                 唯一权威 Skill 源码
  category-*/                   分类 Skill
  atom-*/                       原子 Skill
  meta-skill-governor/          元 Skill
catalog/                        300+ 上游能力目录与快照
taxonomy/                       分类树和边界标准
packs/                          插件式能力包/配方
evals/                          训练、开发、留出、对抗与任务集
src/                            注册表、路由、训练器、适配器和 CLI
schemas/                        能力契约与目录 Schema
tests/                          单元、集成和黄金测试
docs/                           英文文档
docs/zh-CN/                     中文文档
```

仓库根目录本身就是插件，清单直接指向 `.agents/skills`，避免复制或符号链接造成双重真相。

## 5. 什么叫“原子 Skill”

需要同时满足五个单一性：

- **结果单一：** 只有一个主要的用户可见结果。
- **产物单一：** 只有一个主导产物或状态变化。
- **权限单一：** 副作用和授权边界可以独立声明。
- **评测单一：** 能用一个聚焦的完成标准判断好坏。
- **失败单一：** 失败后不必重跑无关工作。

若包含多个可以独立复用的结果，就拆成原子 Skill 或改成配方；若拆开后总是一起变化且没有独立意义，则保留为一个原子 Skill。

每个原子 Skill 都有 `skill.contract.yaml`，描述输入、输出、前置条件、失败模式、工具与 MCP 依赖、权限、风险、正向触发词、负向边界、易混淆能力、来源、许可证和评测集。

去重优先比较“结果 + 产物 + 权限 + 评测边界”的契约指纹，而不是只看名称和关键词。

## 6. 分类标准

分类采用多维描述，但路由按以下顺序决策：

1. **用户结果和产物**：最终要得到什么？
2. **领域**：软件、研究、知识、数据、媒体、商业、运营、个人效率或系统治理。
3. **生命周期**：发现、规划、创建、转换、分析、验证、发布、运行或治理。
4. **模态**：代码、文本、文档、表格、幻灯片、图像、音频、视频、浏览器状态或结构化数据。
5. **依赖**：工具无关、产品专用、MCP、CLI 或 API。
6. **风险**：只读、可逆写入、对外沟通、高风险专业领域、破坏性或特权操作。

初始一级分类为：软件工程、研究与知识、数据与分析、文档与沟通、设计与媒体、商业与增长、自动化与运营、个人效率、安全与信任、Skill 与 Agent 治理。

一个原子 Skill 可以出现在多个分类索引中，但只有一个稳定身份。只有评测持续显示混淆或过载时，才允许拆分或合并分类。

## 7. 分类 Skill

分类 Skill 不是文件夹标签，而是可被 Codex 命中的特殊 Skill，包含：

- 有区分度的 `SKILL.md`；
- `references/index.en.md` 与 `references/index.zh-CN.md`；
- 纳入、排除和边界案例；
- 自动生成的原子能力索引；
- “只读取选中的原子 Skill 或配方”的渐进披露规则；
- 分类版本和节点元数据。

CI 会从契约重新生成/校验索引，防止分类说明与实际能力漂移。

## 8. 元 Skill 与自进化

`meta-skill-governor` 可以扫描、学习、提出修改、评测、上线、弃用、迁移和回滚其他 Skill，也包括自己；但不能静默改写生产 Skill。

固定流程是：

```text
观察 -> 有边界的变更提案 -> 沙盒构建 -> 训练/开发集
  -> 留出集和对抗集门禁 -> 人或策略批准 -> 灰度 -> 上线
  -> 监控 -> 保留或回滚
```

关键规则：

- 所有修改都是带理由、影响范围和契约差异的补丁。
- 用来优化的题目不能再作为上线证明。
- 受保护指标不能回退，安全用例必须全部通过。
- 元 Skill 修改自己时，也必须走同一流程；同一次提案不能顺便削弱门禁。
- 默认先弃用并保留历史，物理删除是另一项显式维护动作。
- 所有决策进入只追加的审计记录。

## 9. 插件思维

项目吸收四个插件原则：

- **Manifest：** 身份、版本、入口、依赖、兼容性显式化。
- **隔离：** 每个原子 Skill 声明工具、权限和副作用。
- **组合：** 能力包引用稳定 ID，不复制大段提示词。
- **生命周期：** 安装、校验、启用、更新、弃用和回滚。

能力包是一份声明式配方，包含原子 Skill、可选 MCP、先后关系、交接产物、语言和验收测试。高频能力包可以暴露一个很薄的编排 Skill，但原子契约仍是事实来源。

## 10. 300+ 上游能力目录

默认只收集元数据和来源，不执行第三方代码。每条记录至少包括仓库与固定 revision、类型、路径、作者、摘要、触发条件、工具、权限、产物、许可证、安全审查、最后验证时间、契约指纹与重复簇。

第一里程碑要求不少于 300 条去重后的前沿记录。无来源、只指向可变分支、ID 重复或许可证缺失的记录不能通过 CI。未知许可证只允许保留在目录中，不允许复制进本仓库。

## 11. 评测与训练软件

题集分为：

- `train`：用于改进描述和规则；
- `dev`：频繁回归；
- `test`：发布前不可参与优化的留出集；
- `adversarial`：歧义、多语言、恶意和负向边界；
- `tasks`：实际执行并检查产物的任务集。

分别测量分类 hit@1/hit@3、原子 hit@1/hit@3/MRR、正确不调用、流程遵循、任务完成、产物质量、安全、回归、成本和延迟。初始门槛建议为：分类 hit@1 ≥ 0.90，原子 hit@1 ≥ 0.80，完成率 ≥ 0.80，受保护安全集 = 1.00，并且多个独立数据集无受保护回归。

训练器只生成小范围候选补丁，不能只凭一个总分宣称改进，每次运行都必须可复现。

## 12. Pi、DSH 与 Codex

统一适配器提供 `discover`、`route`、`execute` 和 `healthcheck`。首个真实集成选择 Pi，因为当前 Node 环境可直接使用其维护中的包和结构化模式；DSH 采用可选适配器，在选定固定 RC 或稳定版本后接入；Codex 适配器用于原生发现校验和轨迹回放；CI 默认使用不需要 API Key 的确定性 Mock 适配器。

评测记录必须包含 Harness 名称与版本，因为同一 Skill 在不同 Harness 中的命中和执行表现可能不同。

## 13. 双语约定

为了主流生态兼容，`SKILL.md` 使用英文作为规范路由面。详细说明通过相邻的 `*.en.md`、`*.zh-CN.md` 提供；`*.zh.md` 是可选的通用中文回退。解析顺序为精确地区、基础语言、英文、默认版本。

翻译可以调整表达和文化习惯，但不得改变能力边界、安全规则或权限。CI 检查各语言所引用的契约版本和必要章节。

## 14. 安全、失败与恢复

- 收录不等于安装；上游指令在采集时一律视为不可信数据。
- 采集器不执行仓库脚本。
- 网络、文件、Shell、密钥、消息发送等权限全部显式声明。
- 检查提示注入、隐藏下载、凭据访问、破坏性命令和越权。
- 元 Skill 未经显式审查不得扩大权限。
- 歧义请求返回候选与解释；依赖缺失返回结构化阻塞原因。
- 上游拉取失败时保留最近一次已验证快照并标记过期。
- 失败候选留在沙盒，不改变活动注册表；每个上线版本都有回滚指针。

## 15. 交付阶段

1. **基础层：** Schema、分类、注册表、CLI、插件清单和首批分类/元/原子 Skill。
2. **证据层：** 300+ 可追溯目录、重复簇和自动生成索引。
3. **评测层：** 双语路由集、可执行任务集、Mock 与 Pi 适配器。
4. **进化层：** 有边界的训练循环、上线门禁、审计和回滚。
5. **生态层：** 能力包、DSH 适配、贡献流程和公开 GitHub Release。

宏大愿景被拆成连续可验证的版本；每个阶段都必须留下一个真正可运行、可测试的系统。
